# MedDecode local demonstration and boundaries

Start the API and frontend from the repository root with `npm run dev`. The launcher prints the actual frontend URL and keeps the hosted worker disabled. Sign in with the authorized synthetic account; use only fictional prescriptions. Ctrl+C stops the launched development processes.

On 14 November 2026, local synthetic PDF, JPEG and PNG runs each passed real EasyOCR, worker claim/finalization, PostgreSQL result persistence and Express results/history retrieval, including cross-owner denial. Each returned one result with prescription status `completed_with_warnings`; controlled invalid-output failures stored no result. Document storage and the authentication/PostgREST bridge were simulated. These checks did not inspect actual recognized medicine names or measure OCR accuracy. The existing `backend/scripts/run-local-real-ocr-demo.ps1 -Format pdf` (also `jpg` or `png`) is an explicitly invoked synthetic local test, not a continuously running service. It requires the local fixture files, models, and isolated PostgreSQL environment named in that script. Do not point it at a hosted queue. Its test creates local synthetic records; inspect the guard and obtain the necessary local authorization before running it.

The normal development command does not start a worker. Hosted claim and recovery RPCs operate on the shared queue, so an empty queue or client-side filter is not sufficient isolation. Do not enable the hosted worker until a separately reviewed isolation mechanism, credentials and synthetic test are authorized. S3 upload/download was previously verified separately; that does not prove an S3-backed hosted processing workflow.

The experimental `local-synthetic-document.store.ts` is only an injected, unit-tested adapter and is not wired into the application. It requires a trusted private local directory and does not itself establish user ownership, Windows ACL isolation, full image validation, or a continuous processing mode. There is no `npm run dev:ocr` command yet. A dedicated synthetic authentication and local database bridge, exclusive worker claim/recovery boundary, persistent storage lifecycle, and end-to-end verification remain necessary before activation.

Additional experimental local identity and continuous-worker components exist, but are not registered with the application. Their database identity reader and worker composition are injected and have only fake-dependency tests: they do not establish a real isolated PostgreSQL instance or prevent a miswired caller from supplying false identity information. The identity component must not be exposed until bound to an independently verified local environment. These components do not start a worker or change hosted configuration.

Focused verification on 14 November: frontend production build and 36 prescription UI tests passed; 31 backend processing/results/worker tests and five Python Contract v1/integration tests passed. Mocked tests do not establish a hosted workflow. The authenticated browser demonstration was not rerun during these checks.

Use the normal history and result pages to inspect records that actually exist for the signed-in user. The status interface reports the persisted high-level state; it does not claim individual OCR stages or a fabricated progress percentage. Exact OCR accuracy metrics require a versioned ground-truth set and an actual evaluation run; no such metrics are asserted here.

Cabinet read/write interfaces exist, but a completed prescription cannot yet be saved to Cabinet safely without a validated legacy medicine mapping. Official formulation IDs must not be substituted for legacy medicine IDs. Reminder UI and a notification table do not establish a working reminder API or delivery mechanism. Official catalogue browse requires its separately reviewed hosted RPC migration; source price observations cannot be displayed as formulation prices without verified relationships.

If a submission fails or its outcome is unknown, check processing status before retrying. Never use administrator credentials to impersonate a user. Hosted schema changes, synthetic hosted writes, and worker activation each require separate approval.
