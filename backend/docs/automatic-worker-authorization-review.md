# Automatic scoped worker — local review candidate

This proposal is disabled by default and has not been deployed. It admits a job only when the authenticated owner submits it through the automatic submission RPC after the activation timestamp. Replays may reuse only an already admitted job. Existing manual or unrelated queued jobs are not adopted. The issuer accepts a worker instance identifier, never a job ID; it reads the admission ledger and limits issuance to one job at a time. It renews the scope while the worker is alive and uses the existing claim, fencing, recovery and finalization RPCs.

The intended deployment identity is a new `meddecode_auto_worker_login` with LOGIN, NOINHERIT, no elevated attributes, and SET-only membership in the existing `meddecode_scoped_worker` role. It must have no direct application-table privileges or unrestricted worker RPC grants. The issuer validates `session_user` and the instance ID. No identity has been created for this proposal on the hosted project. It requires a dedicated password, verified TLS, and session pooling that preserves the login identity. The auto-submission, automatic-authorization and worker flags remain off until explicitly authorized.

The private policy row defaults to disabled; its default scope duration is 1,200 seconds, bounded by 300–3,600 seconds. Node renews every 30 seconds. A failed issuer prevents the Node runtime from making a new claim; an in-flight job remains constrained by its existing lease and scope. A database principal holding a previously issued scope can call the existing scoped RPCs until that scope expires: disabling the policy alone does not revoke existing scopes. Emergency disablement must stop the worker **and**, under separately authorized database change, disable the policy and the automatic login's outstanding scope rows. It must not alter scopes of other logins.

The candidate is not a hosted deployment package yet. Before seeking approval, independently review role provisioning and its rollback, migration ownership and privileges on hosted PostgreSQL, migration preflight and post-verification, policy activation and audit, existing active jobs, retry/exhaustion and policy-disable races, and operational rollback with in-flight jobs. Test the exact rollout with the non-superuser deployment identity and a dedicated worker login. Preserve the activation timestamp when restarting; changing it can strand admitted jobs. Do not drop the ledger while jobs remain active. Restore permissions from recorded pre-deployment grants, not guessed defaults.

The isolated tests used the existing private PostgreSQL 17 cluster and fictional records. The rollback test covers disabled admission, ownership, replay, expiry and recovery. Two concurrent scoped sessions produced only one processing job. These tests do not demonstrate hosted deployment, continuous crash recovery under load, or a real second upload-to-results run. No hosted data, grants or workers were changed by this candidate.
