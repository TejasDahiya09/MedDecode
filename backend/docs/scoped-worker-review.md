# Scoped prescription worker: review candidate

This candidate is **not approved for deployment**. The existing unrestricted worker functions remain unchanged. The candidate requires a separately provisioned `meddecode_scoped_worker` NOLOGIN/NOINHERIT role and a dedicated login with explicit SET membership, no unrestricted worker membership, and no direct application-table privileges. Role creation, login credentials, registry authorization, hosted migration execution, synthetic uploads and worker activation are separate approval boundaries.

The private scope table binds a job, prescription, owner, worker instance and expiry. Claim and recovery join and lock the scope and job; heartbeat, completion and failure require a live scope and matching job lineage. The worker's `WORKER_RPC_MODE=scoped` selects only scoped function names and rejects a login that is a member of the unrestricted worker role. Development workers fail closed unless scoped mode is selected. Normal server startup does not run a worker.

The candidate requires a trusted administrator to insert and later revoke an explicitly approved synthetic job scope. Scope expiration or revocation prevents subsequent heartbeat and completion, including idempotent completion replay. A processing job can therefore remain stranded after scope expiry; an operator must review and explicitly reauthorize or resolve it. Do not interpret an expired scope as successful processing.

`test-scoped-worker-rollback.ps1` compiles and runs a transformed copy inside a rolled-back transaction in the previously approved local worker-test database. It substitutes the existing local worker role to avoid creating cluster-wide roles. It checks empty-scope denial, role denial, one authorized claim, a stale heartbeat, revocation, recovery, terminal failure, unregistered-job isolation, completion and replay. It does **not** validate the actual proposed role, role provisioning, concurrent races, deployment privileges, all rollback cases, or the hosted database. Those tests, a fresh hosted preflight and a backup are required before any deployment request.

After separate approvals, intended review order is `scoped-worker-isolation-preflight.sql`, `scoped-worker-isolation-review.sql`, and `scoped-worker-isolation-verify.sql`. The SQL expects the scoped role to exist beforehand and does not provision a login, password, or registry entries. Stop on any error. Rollback is `scoped-worker-isolation-rollback-review.sql`, only after stopping the worker and ensuring the scope table is empty; rollback requires separate approval. Never delete authorized scope evidence merely to force rollback.
