# Automatic prescription submission: integration contract

This backend path is disabled by default and does not authorize or start a worker. Do not enable it for hosted traffic until the client and a separately reviewed general dispatch authorization are deployed.

The legacy upload contract is unchanged. A compatible client may send `X-MedDecode-Auto-Submit: v1` on `POST /api/v1/prescriptions/upload`. This is accepted only when both `PRESCRIPTION_AUTO_SUBMIT_ENABLED=true` and the durable `PROCESSING_JOB_STORE_ENABLED=true` are configured. An opt-in request receives 503 before storage when auto submission is disabled. Authentication, upload validation, S3 storage and owner-scoped prescription creation remain unchanged.

After a successful upload the backend invokes the existing authenticated `submit_prescription_analysis_job_v1` service exactly once. On a confirmed submission the 201 response has `processing: { requested: true, job_id: <uuid> }`. If the submission response is lost or otherwise unconfirmed, the 201 response has `processing: { requested: null, job_id: null, submission: "unconfirmed" }`: the prescription and S3 object are already stored, and the client must not re-upload. It should query `GET /api/v1/prescriptions/:id/processing-status`; if appropriate, the existing idempotent `POST /api/v1/prescriptions/:id/process` can reconcile the same prescription. Concurrent duplicate submissions for one prescription use the existing database active-job uniqueness and submission RPC. This does not deduplicate separate upload requests that create different prescription IDs.

Frontend handoff: update the strict upload response parser to accept these negotiated variants; send the header only after the backend feature is enabled. Navigate to the returned prescription and poll its existing status endpoint. Replace the fixed statement that processing was not requested with the confirmed or unconfirmed state. Do not invent stage percentages or treat an unconfirmed submission as a failed upload.

The existing one-job scope registry does not authorize later uploads automatically. A production dispatch policy must separately define who may authorize new jobs, how authorized owner/job/prescription bindings are created atomically with submission, how expiration and recovery work across outages, and how only the approved worker identity claims those bindings. It must exclude previously queued jobs without explicit authorization, preserve cancellation and lease fencing, and have independent database concurrency and privilege tests. Deploying such policy, enabling automatic submission, and activating a persistent worker are distinct hosted approval boundaries. No general queue worker is activated by this change.
